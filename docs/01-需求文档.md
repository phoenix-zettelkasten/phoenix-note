## 1. 引言

### 1.1 项目背景与目标

用户希望拥有一个基于卡片盒笔记法（Zettelkasten）的个人知识管理应用。市面工具或闭源、或将笔记锁定在私有数据库中、或缺少 AI 辅助能力。phoenix-note 的目标是：

1. **让知识永不被软件绑架**——所有笔记以纯 Markdown 文件形式存储，任何文本编辑器都能打开；
2. **忠于方法论**——产品围绕「原子化、链接、自成体系」三大支柱设计，而不是普通笔记软件加个链接功能；
3. **AI 原生**——将 AI 辅助（总结、关联推荐）作为一等公民，弥补传统 Zettelkasten 工具的空白；
4. **四端可用**——Web、Linux、Windows、Android。

### 1.2 术语表（也是方法论入门）

| 术语 | 英文 | 定义 |
|---|---|---|
| 卡片盒笔记法 | Zettelkasten | 由德国社会学家尼克拉斯·卢曼发展的笔记方法，核心是让单条笔记（卡片）之间通过编号和引用形成可生长的网络，最终成为「第二大脑」，卢曼借此完成了数十本著作。 |
| 原子化 | Atomicity | 每条笔记只表达**一个**完整想法。一条笔记 = 一个想法，方便被其他笔记精确引用。 |
| 闪念笔记 | Fleeting note | 临时记录的灵感，尚未加工，等待转化为永久笔记后删除。 |
| 永久笔记 | Permanent note | 用自己的话完整表述一个想法、可独立阅读、且与已有笔记建立了链接的笔记。是卡片盒的核心资产。 |
| 文献笔记 | Literature note | 阅读时对来源内容的记录，注明出处，与永久笔记分开存放。 |
| 枢纽笔记 | Hub note / Structure note | 汇集多个相关笔记链接的「地图式」笔记，如某个主题的入口。 |
| 双链 | Wikilink / Bidirectional link | 笔记正文中的 `[[笔记ID]]` 引用，可跳转到目标笔记；同时目标笔记可以反向看到「谁引用了我」。 |
| 反向链接 | Backlink | 引用了当前笔记的所有笔记列表。 |
| 悬空链接 | Dangling link | 指向尚不存在笔记的链接。在 Zettelkasten 中**这是正常工作流**（先建结构笔记再补子笔记），不是错误。 |
| 笔记 ID | Note ID | 笔记的唯一标识。本项目默认为 14 位时间戳（创建时刻 UTC），方案详见详细设计文档。 |
| Frontmatter | — | Markdown 文件顶部的 YAML 元数据块（`---` 包围），存放标题、标签、时间戳等结构化字段。 |
| DoD | Definition of Done | 「完成的定义」：一个里程碑要满足哪些可验证条件才算交付。 |

### 1.3 参考资料

- Sönke Ahrens, *How to Take Smart Notes*（申克·阿伦斯《卡片笔记写作法》）——方法论主参考
- Markdown 规范（CommonMark）
- YAML frontmatter 惯例（Jekyll/Hugo/Obsidian 通用格式）

## 2. 产品概述

### 2.1 产品愿景

> 你的想法属于你：phoenix-note 用纯文本承载你的第二大脑，用双链编织想法，用 AI 放大洞察。

### 2.2 目标用户

**主要用户：本项目作者本人**（单用户自部署起步）。画像：

- 技术背景：开发者，熟悉 Linux 日常使用，正在学习 Web 全栈与 Zettelkasten 方法；
- 设备环境：Linux 桌面主力 + Android 移动端 + 偶尔 Windows，需要浏览器随时随地访问；
- 核心诉求：笔记文件必须纯文本、可 git 版本化、可被任何工具打开；希望有 AI 帮助整理和关联想法。

### 2.3 使用场景

| 场景 | 平台 | 描述 |
|---|---|---|
| S-01 | Web / 桌面 | 日常写作与整理：新建永久笔记、补充 `[[链接]]`、维护枢纽笔记 |
| S-02 | Android | 通勤/碎片时间用手机快速记闪念笔记 |
| S-03 | Web / 桌面 | 回顾：搜索旧笔记、浏览反向链接、查看关系图谱 |
| S-04 | Web / 桌面 | 复习与洞察：让 AI 总结一组笔记、推荐可能相关的旧笔记 |

### 2.4 产品边界

**范围内**：个人知识管理（单用户）+ 上述四端访问 + AI 辅助。
**范围外（当前版本明确不做）**：多人协作与权限系统、富文本编辑（视频/画板）、实时协同编辑、日历/任务管理。多用户支持推迟到 M6 再评估。

## 3. 功能需求

优先级：**P0** = M1 必须（核心闭环）；**P1** = M2/M3（体验增强）；**P2** = M4–M6（平台扩展与增值）。
每条需求含用户故事与验收标准（Acceptance Criteria, AC），AC 即该需求的测试依据。

### FR-01 笔记管理（P0，M1）

**用户故事**：作为用户，我要创建、查看、编辑、删除笔记，以便把每个想法沉淀为一条原子化卡片。

**验收标准**：
1. 可创建笔记：填写标题（必填）、标签（可选）、正文（Markdown）；
2. 创建后，服务端 `notes/` 目录出现一个新的 `.md` 文件，frontmatter 含 title/tags/created/modified，正文为用户输入；
3. 修改笔记并保存后，磁盘上对应文件内容更新，`modified` 时间戳刷新，`created` 与文件名（ID）不变；
4. 删除笔记后，文件从磁盘消失，笔记列表同步更新；
5. 笔记列表按创建时间从新到旧排序；
6. 所有数据仅存于 Markdown 文件——用任意文本编辑器直接修改文件后，应用刷新即反映新内容（无隐藏数据库）。

### FR-02 双向链接（P0，M1）

**用户故事**：作为用户，我要在笔记中用 `[[ID]]` 引用其他笔记，并在阅读时点击跳转，以便让想法互联成网。

**验收标准**：
1. 正文中 `[[20261019153042]]` 或 `[[20261019153042|显示文字]]` 形式的链接在预览中渲染为可点击链接，点击后打开目标笔记；
2. 链接目标笔记不存在时（悬空链接），渲染为可识别的「缺失」样式（虚线），不崩溃、不静默隐藏；点击该链接给出友好提示；
3. 复制笔记链接：界面上可一键获得当前笔记的 `[[ID|标题]]` 引用文本，缓解手输 14 位 ID 的负担；
4. 链接语法在代码块（``` 围栏）内时按普通文本处理（M1 已知限制可暂不实现，须在文档中登记）。

### FR-03 反向链接（P0，M1）

**用户故事**：作为用户，我要在查看一条笔记时看到哪些笔记引用了它，以便沿着链接网络回顾知识。

**验收标准**：
1. 获取笔记详情时，API 返回反向链接列表（来源笔记 ID、标题、链接上下文片段约 80 字符）；
2. 反向链接为空时返回空列表，不报错；
3. 某笔记被多条笔记引用时，反向链接全部列出；
4. 引用方笔记被删除后，其反向链接随之消失。

### FR-04 全文搜索与标签（P1，M3）

**用户故事**：作为用户，我要按关键词搜索全文、按标签过滤笔记，以便快速找到需要的想法。

**验收标准**：
1. 输入关键词可搜索标题与正文，返回按相关度排序的结果；
2. 点击标签可列出含该标签的所有笔记；
3. 搜索应覆盖数万字符规模笔记库且响应时间 < 500ms（详见 NFR-02）。

### FR-05 关系图谱（P1，M2）

**用户故事**：作为用户，我要看到笔记之间链接网络的可视化图谱，以便发现孤岛笔记和潜在关联。

**验收标准**：
1. 图谱视图以节点（笔记）+ 有向边（链接）呈现全库关系；
2. 悬空链接以特殊样式呈现；悬空笔记（无任何链接的笔记）明显可辨；
3. 点击节点跳转到该笔记；
4. 首屏渲染可交互（拖拽、缩放）。

### FR-06 AI 辅助（P2，M5）

**用户故事**：作为用户，我要 AI 帮我总结冗长笔记、推荐可能相关的旧笔记，以便对抗遗忘、发现跨领域连接。

**验收标准**：
1. 单条笔记可一键生成摘要（中文）；
2. 编辑或查看笔记时，系统推荐语义相关的其他笔记（依据链接 + 全文相似度 + AI 语义）；
3. AI 调用为显式触发或可关闭，不产生未经请求的自动改写；模型与 API Key 可配置。

### FR-07 多端访问（P2，M4）

**用户故事**：作为用户，我要在浏览器、Linux/Windows 桌面和 Android 上使用同一套应用，以便在任何场景记录想法。

**验收标准**：
1. Web 版响应式适配手机宽度；
2. Tauri 2 打包产出 Linux/Windows 桌面应用与 Android APK，连接同一后端；
3. 各端功能一致（同一套前端代码）。

### FR-08 自定义笔记 ID 方案（P2，待细化）

**用户故事**：作为用户，我希望笔记 ID 方案可自定义（默认为时间戳方案；用户设想的「中国读书法」标定方式待后续细化），以便 ID 承载我自己的意义。

**验收标准**：
1. M1 起 ID 生成逻辑实现为独立策略模块，接口与实现分离；
2. 更换 ID 方案时无需修改存储、路由以外的代码；
3. 双链语法与 ID 校验规则随方案在配置层联动；
4. 该需求的具体方案由用户补充后进入详细设计评审。

## 4. 非功能需求

### NFR-01 数据可靠性（最高优先级）

1. **无锁定**：笔记仅存为纯 Markdown 文件（UTF-8，LF 换行），无隐藏数据库；`notes/` 目录可直接被 git 管理；
2. **写入原子性**：保存笔记时先写临时文件再原子替换，进程崩溃不得损坏既有笔记内容；
3. **ID 不变性**：笔记 ID（文件名）创建后终生不变；改标题只改 frontmatter，因此链接永不失效；
4. 路径安全：任何请求参数在拼接文件路径前必须通过 ID 格式校验，杜绝路径穿越攻击。

### NFR-02 性能（M1 目标，单用户本地部署）

| 指标 | 目标值 |
|---|---|
| 笔记规模 | M1 支持 5,000 条笔记 |
| 笔记列表响应 | < 300ms |
| 笔记详情（含反向链接扫描） | < 500ms @ 5,000 条 |
| 前端首屏 | < 3s（开发环境） |

反向链接 M1 允许 O(N) 全库扫描实现；M6 引入 C++ 索引模块优化，接口缝隙须在 M1 预留（代码注释标记）。

### NFR-03 安全

1. 渲染用户 Markdown 前必须消毒（防 XSS——用户可能粘贴来源不明的网络内容）；
2. API 校验所有输入（Pydantic schema），错误输入返回 4xx 与明确错误信息；
3. M1 为单用户本地部署，不含认证体系；对外部署所需的鉴权在 M6 前评估（登记于风险）。

### NFR-04 可维护性

1. 文档先行：需求文档 → 详细设计 → 编码，每阶段评审后进入下一阶段；
2. 后端核心逻辑（wikilink 解析、存储层）单元测试覆盖；API 层集成测试；
3. 类型安全：后端 Pydantic v2、前端 TypeScript strict，前后端模型一一对应；
4. 代码规范：ruff（Python）+ 前端默认 lint。

### NFR-05 兼容性

1. 服务端：Python ≥ 3.11（当前部署环境 3.14）、Linux；
2. 浏览器：Chrome/Edge/Firefox 两个最新大版本；
3. M4 起：Linux/Windows 10+ 桌面壳、Android 12+；
4. 笔记文件本身与任何标准 Markdown 工具（Obsidian 只读、VS Code 等）保持文件级兼容（frontmatter 为通用 YAML）。

## 5. 约束与假设

**约束**：
- C1 开发机为 Gentoo Linux，Python 无系统 pip，虚拟环境经 ensurepip 自建（已验证可用）；
- C2 M1 不引入 uv、Docker 等额外工具链，用标准 venv + pip + npm；
- C3 交付节奏以「里程碑 + 评审闸门」推进，每阶段须用户确认。

**假设**：
- A1 M1 阶段为单用户本地使用，无并发写入冲突；
- A2 笔记库以英文/中文为主，M1 不做 CJK 特殊分词（全文搜索留到 M3 细化）。

## 6. 验收标准与里程碑计划

### 6.1 里程碑范围

| 里程碑 | 范围 | 对应需求 | DoD（完成的定义） |
|---|---|---|---|
| **M1** 核心闭环 | 笔记 CRUD + 双链 + 反向链接 API + Web 界面 | FR-01/02/03 | FR-01/02/03 验收标准全过；pytest 全绿；`npm run build` 通过；端到端清单逐条核验 |
| **M2** 网络可视化 | 反向链接面板 UI + 关系图谱 + 双链自动补全 | FR-05（+FR-02 补全） | 图谱可交互；补全选择器可用；M1 回归通过 |
| **M3** 检索 | 全文搜索 + 标签过滤（SQLite FTS5 起步） | FR-04 | NFR-02 搜索性能达标 |
| **M4** 四端 | Tauri 2 打包 Linux/Windows/Android | FR-07 | 三平台安装包可运行并连接后端 |
| **M5** AI | 总结 + 关联推荐 | FR-06 | AI 功能可配置、可关闭；不产生未经请求的自动行为 |
| **M6** 规模化 | C++ 全文索引模块 + 多用户/鉴权评估 | NFR-02、NFR-03 | 索引替换 O(N) 扫描；多用户方案另行立项 |

### 6.2 M1 端到端验收清单（Gate 3 的检查表）

1. 双服务启动（后端 :8000 / 前端 :5173），示例库 4 条笔记按新→旧显示于侧栏；
2. 点击笔记可查看，预览中双链可点击跳转，悬空链接呈「缺失」样式且不崩溃；
3. 浏览器后退/前进按历史切换笔记；
4. 从 UI 新建笔记后 `notes/` 目录出现对应 `.md` 文件，frontmatter 正确；
5. 编辑正文添加对已有笔记的 `[[ID]]` 链接并保存，目标笔记的反向链接出现该来源；
6. 用系统文本编辑器直接修改磁盘文件，刷新页面后内容生效；
7. 删除笔记后文件从磁盘消失，指向它的链接自动变为「缺失」态；
8. `pytest` 全部通过；`npm run build` 类型检查通过。

### 6.3 已知限制登记（M1 明确接受，后续版本处理）

| 编号 | 限制 | 处理计划 |
|---|---|---|
| L-01 | 14 位 ID 手工输入困难 | M1 提供「复制链接」缓解；M2 交付自动补全选择器 |
| L-02 | 代码块内 `[[ID]]` 会被误识别为链接 | 若 M1 实际使用中造成困扰，M2 优先修复 |
| L-03 | 无鉴权，仅限本地/内网使用 | M6 前评估，对外部署前必须解决 |
| L-04 | 双链不支持 `[[标题]]` 形式（仅 ID） | 有意为之：ID 链接是时间戳方案的根基，不计划支持 |
