## 1. 引言

### 1.1 项目背景与目标

用户希望拥有一个基于卡片盒笔记法（Zettelkasten）的个人知识管理应用。市面工具或闭源、或将笔记锁定在私有数据库中、或缺少 AI 辅助能力。phoenix-note 的目标是：

1. **让知识永不被软件绑架**——所有笔记以纯 Markdown 文件形式存储，任何文本编辑器都能打开；
2. **忠于方法论**——产品围绕「原子化、链接、自成体系」三大支柱设计，并延伸到流转（闪念→永久）、群聚检测、探索等 Zettelkasten 高级实践；
3. **AI 原生**——将 AI 辅助（总结、关联推荐）作为一等公民；
4. **四端可用 + 编辑器自由**——Web、Linux、Windows、Android，且不绑架编辑器（vim 插件、Obsidian 兼容）。

### 1.2 术语表（也是方法论入门）

| 术语 | 英文 | 定义 |
|---|---|---|
| 卡片盒笔记法 | Zettelkasten | 卢曼发展的笔记方法：单条笔记（卡片）通过编号和引用形成可生长的网络，成为「第二大脑」。 |
| 原子化 | Atomicity | 每条笔记只表达**一个**完整想法，方便被精确引用。 |
| 闪念笔记 | Fleeting note | 临时记录的灵感，尚未加工，等待转化为永久笔记后归档/删除。 |
| 永久笔记 | Permanent note | 用自己的话完整表述、可独立阅读、已与已有笔记建立链接的笔记。卡片盒的核心资产。 |
| 文献笔记 | Literature note | 阅读时对来源的记录，注明出处。 |
| 结构笔记 | Structure note / Hub note | 汇集相关笔记链接的「地图式」笔记，如某主题的入口。 |
| 双链 | Wikilink | 正文中的 `[[编号]]` 引用，可跳转，目标可反向看到引用者。 |
| 反向链接 | Backlink | 引用了当前笔记的所有笔记列表。 |
| 悬空链接 | Dangling link | 指向尚不存在笔记的链接。**正常工作流**（先建结构笔记再补子笔记），不是错误。 |
| 中图法 | CLC（中国图书馆分类法） | 中国通用的图书学科分类体系，编号如 B（哲学）、TP（自动化技术与计算机）。本项目用作笔记的学科维度编号。 |
| 双射26进制 | Bijective base-26 | 无零字符的字母计数：A=1…Z=26，AA=27，AB=28……本项目索引编号的字母层采用此编码，数字层采用 1–9。 |
| 逻辑前后链接 | Folgezettel | 卢曼原方法中的父子/兄弟顺序关系：编号可从结构上推出一条笔记在卡片盒中「生长」的位置。 |
| 笔记流转 | Note lifecycle | 闪念→（加工）→永久/结构笔记的状态迁移，含定时整理提醒。 |
| 群聚效应 | Clustering | 链接网络中自然形成的主题聚集。检测用于发现主题群、枢纽与孤岛笔记。 |
| 存算分离 | Storage-compute separation | 存储（Markdown 文件 = 唯一真身）与计算（派生索引数据 = 可丢弃缓存）分离。 |
| 文件监控 | File watching | 后端监听文件系统事件，外部修改即时反映到应用。 |
| 笔记 ID / 编号 | Note ID | 笔记唯一标识，也是文件名主体。默认格式见 FR-03。 |
| Frontmatter | — | Markdown 文件顶部 YAML 元数据块。 |
| DoD | Definition of Done | 里程碑「完成的定义」。 |

## 2. 产品概述

### 2.1 产品愿景

> 你的想法属于你：phoenix-note 用纯文本承载你的第二大脑，用双链与编号编织思想结构，用 AI 放大洞察，用任何你喜欢的编辑器书写。

### 2.2 目标用户

**主要用户：本项目作者本人**（单用户自部署起步）。画像：

- 技术背景：开发者，Linux 桌面主力 + Android 移动端，vim 用户；
- 工作流偏好：笔记必须纯文本、可 git 版本化、可被 vim / Obsidian 等任何工具打开；后端做计算、文件做存储；
- 核心诉求：完整的 Zettelkasten 生命周期（捕捉→流转→关联→回顾→探索）。

### 2.3 使用场景

| 场景 | 平台 | 描述 |
|---|---|---|
| S-01 | Web / 桌面 / vim | 日常写作：新建笔记、补 `[[链接]]`、维护结构笔记 |
| S-02 | Android | 通勤碎片时间记闪念笔记 |
| S-03 | Web / 桌面 / vim | 检索：全局搜索、标签逻辑查询、反链回溯 |
| S-04 | Web / 桌面 | 整理：处理待流转的闪念笔记（定时提醒）、群聚检测找孤岛 |
| S-05 | Web / 桌面 | 探索与洞察：漫游图谱、AI 总结、关联推荐 |

### 2.4 产品边界

**范围内**：个人知识管理全生命周期（捕捉/流转/链接/检索/探索/AI）+ 四端访问 + vim 插件 + git/Obsidian 兼容。
**范围外**：多人协作与权限系统、富文本编辑（画板/视频）、实时协同编辑、日历/任务管理。多用户支持推迟到 M6 评估。

## 3. 功能需求

### 3.0 功能域总览

13 条评审新增需求与原有需求归入 7 个功能域：

```
A 笔记核心    —— 内容怎么存：CRUD、分类目录、模块化编号（3 条）
B 链接与网络  —— 想法怎么连：双链、反链、逻辑前后链接、图谱（4 条）
C 生命周期流转 —— 笔记怎么长大：闪念→永久的状态迁移（1 条）
D 组织与检索  —— 怎么找到：全局检索、#标签与逻辑运算（2 条）
E 智能与探索  —— 怎么增值：群聚检测、探索模式、AI 辅助（3 条）
F 平台与集成  —— 在哪用：多端、vim 插件、文件监控、同步兼容（4 条）
G 架构性需求  —— 底座怎么搭：存算分离（贯穿全部功能域的硬约束）
```

优先级：**P0** = M1 必须；**P1** = M2/M3；**P2** = M4–M6。

### A 域：笔记核心

#### FR-01 笔记管理（P0，M1）｜原 v1.0 FR-01

**用户故事**：作为用户，我要创建、查看、编辑、删除笔记，把每个想法沉淀为原子化卡片。

**验收标准**：
1. 可创建笔记：标题（必填）、标签（可选）、正文（Markdown）；
2. 创建后磁盘出现对应 `.md` 文件（frontmatter 含 title/tags/created/modified）；
3. 编辑保存后文件更新、`modified` 刷新；文件名（编号）在不变更层级时不变；
4. 删除后文件移除、列表同步；
5. 所有数据仅存于 Markdown 文件——外部文本编辑器改动后应用能感知（M1 手动刷新感知即可，M3 起文件监控自动感知，见 FR-16）。

#### FR-02 分类目录存储（P0，M1）｜v1.1 新增

**用户故事**：作为用户，我要笔记按类别分目录保存，每类一个独立目录，让卡片盒保持井然有序。

**验收标准**：
1. 笔记库根目录下按**笔记类别**划分为独立子目录，M1 默认方案：`fleeting/`（闪念）、`literature/`（文献）、`permanent/`（永久）、`structure/`（结构）；类别目录集合可配置；
2. 笔记的类别是其文件路径的函数（哪个目录 = 哪类笔记）；
3. 类别信息不重复存储于 frontmatter（单一真身原则，避免目录与字段不一致）；
4. 学科维度（中图编号）承载于笔记编号（FR-03），不使用目录表达学科——类型进目录、学科进编号，两个维度正交。

> ⚠️ 评审点 R-1：「类型进目录、学科进编号」是本文档的推荐设计（备选：按中图分类建目录树）。若你有不同偏好请在评审时指出。

#### FR-03 模块化笔记编号系统（P0，M1）｜v1.1 新增，吸收并取代原 FR-08

**用户故事**：作为用户，我要一套可自定义的模块化编号规则，并让编号本身可读出层级关系，使编号成为卡片盒的「骨架」。

**默认规则**：`[中图编号]-[索引编号]`

- **中图编号**：中图法分类号，如 `B`、`TP312`（可配置子级深度）；
- **索引编号**：双射26进制与数字逐层交替：
  - 第 1 层：字母（A…Z，超出延展 AA, AB…，双射26进制）；
  - 第 2 层：数字（1–9）；
  - 第 3 层：字母，第 4 层：数字……依此交替；
  - **层级可推导**：`A` 的子层是 `A1`；`A1` 的子层是 `A1A`；从 `A1A` 可逐层剥出祖先链 `A1 ← A`；
- 示例：`B-A1A.md`（哲学类，A 的第 1 子项的第 A 子项）、`TP312-B2.md`（程序语言类，B 的第 2 子项）。

**验收标准**：
1. 编号规则实现为**独立可插拔的策略模块**（接口与默认实现分离），更换规则不动其他模块；
2. 默认规则按上述语法生成编号；同一父层下编号不冲突（并发创建不重号）；
3. 每条笔记的编号 = 文件名主体（`<编号>.md`），frontmatter 不重复存储编号；
4. 编号合法性校验（字母/数字交替结构、中图编号存在性）在任何编号触碰文件路径前完成；
5. 双链语法随编号规则联动（见 FR-04）；
6. 后端提供「从编号推导层级链」的查询能力（父子关系的基础，见 FR-06）。

> ⚠️ 评审点 R-2：编号承载层级 → **调整层级会改变编号 → 引用它的链接会失效**。两个可选策略：① 编号变更时后端自动改写全库所有引用（借助派生索引，代价是全库写操作）；② 增加一个不可变的内部 uid 供链接寻址，编号仅作展示。本文档默认选 ①（文件自包含原则优先），评审时请确认。

> ⚠️ 评审点 R-3：数字层用 1–9，即每层最多 9 个直接子笔记；超出时字母层可自然延展（AA），数字层是否也需要延展方案（如 `A91`）由详细设计阶段定，评审时请确认 9 个子项是否够用。

### B 域：链接与网络

#### FR-04 双向链接（P0，M1）｜原 v1.0 FR-02，语法适配新编号

**用户故事**：作为用户，我要在笔记中用 `[[编号]]` 引用其他笔记并点击跳转，让想法互联成网。

**验收标准**：
1. `[[B-A1]]` 或 `[[B-A1|显示文字]]` 渲染为可点击链接并跳转；语法随 FR-03 编号规则联动（策略模块提供链接目标校验）；
2. 悬空链接渲染为「缺失」样式（虚线），不崩溃；点击给出友好提示；
3. 一键复制当前笔记的 `[[编号|标题]]` 引用文本；
4. **所有链接关系保存在 Markdown 文件本身**（正文或 frontmatter），不存只在数据库里的链接——文件自包含是硬约束（见 FR-18）；
5. 代码块内 `[[编号]]` 按 M1 已知限制处理（登记 L-02）。

#### FR-05 反向链接（P0，M1）｜原 v1.0 FR-03

**用户故事**：作为用户，我要看到哪些笔记引用了当前笔记，以便沿网络回顾。

**验收标准**：
1. 笔记详情返回反向链接（来源编号、标题、上下文片段约 80 字符）；
2. 引用方删除后其反链随之消失；空反链返回空列表不报错；
3. M1 实现：请求时全库扫描 O(N)（5,000 条内达标）；M3 起由派生索引提供（FR-18）。

#### FR-06 逻辑前后链接（Folgezettel）（P1，M2）｜v1.1 新增

**用户故事**：作为用户，我要表达并查看一条笔记在卡片盒中的逻辑位置（父/子/兄弟顺序），让编号骨架与链接网络互补。

**验收标准**：
1. 笔记可声明顺序关系（父笔记、前后笔记），**关系存于 Markdown 文件**（frontmatter 字段，如 `up:`（父）、`prev:`/`next:`（同级顺序）；具体字段名在详细设计冻结）；
2. UI 呈现面包屑层级链与同级序列；
3. 与 FR-03 的层级推导互通：编号推导的父子关系与显式声明的关系冲突时，显式声明优先并给出提示；
4. 图谱（FR-07）以不同边样式区分语义链接与顺序链接。

#### FR-07 关系图谱（P1，M2）｜原 v1.0 FR-05

**验收标准**：
1. 节点（笔记）+ 有向边（链接）呈现全库网络；语义链接与顺序链接（FR-06）边样式可区分；
2. 悬空链接、孤岛笔记（无任何链接）明显可辨；
3. 点击节点跳转；首屏可交互（拖拽、缩放）。

### C 域：生命周期流转

#### FR-08 笔记流转（P1，M2）｜v1.1 新增

**用户故事**：作为用户，我要让闪念笔记按时被提醒、被加工转化为永久笔记，让卡片盒保持新陈代谢而不是垃圾堆。

**验收标准**：
1. 笔记状态由所在类别目录决定（FR-02）：`fleeting/` → `permanent/`/`structure/` 的迁移即流转；
2. 流转操作：迁移目录 + 引导用户补充链接（转化即「建立至少一条连接」，与原子化方法论一致）；
3. 定时整理：闪念笔记创建满 N 天（可配置，默认 3 天）未流转的进入「待整理」提醒列表；
4. 流转历史可在 git 历史中追溯（目录迁移即文件移动，天然被 git 记录）。

### D 域：组织与检索

#### FR-09 全局检索（P1，M3）｜v1.0 FR-04 扩充 + v1.1「全局」明确

**用户故事**：作为用户，我要按关键词检索全库标题与正文，快速找到任何想法。

**验收标准**：
1. 检索覆盖全部类别目录、标题 + 正文 + 标签；
2. 结果按相关度排序，支持中文（M3 范围内先以子串/FTS 起步，分词优化后续迭代）；
3. 性能：万字符级笔记库响应 < 500ms（NFR-02）；
4. 由派生索引（FR-18）提供，文件变更后索引增量更新，保证「外部编辑后检索结果是最新的」。

#### FR-10 #标签与逻辑运算（P1，M3）｜v1.1 新增（原 FR-04 标签部分并入）

**用户故事**：作为用户，我要用 `#tag` 行内打标签，并用逻辑组合（AND/OR/NOT）查询标签，实现多维筛选。

**验收标准**：
1. 正文与 frontmatter 中的 `#tag` 均被识别（识别规则：`#` 后跟合法字符直到空白；冲突规则在详细设计冻结）；
2. 标签查询支持逻辑运算：`#ml AND #zettel`、`#work OR #study NOT #archived`，支持括号分组；
3. 单击标签列出该标签全部笔记；多标签组合查询从检索页发起；
4. 标签数据源为派生索引（FR-18），文件中只写 `#tag` 原文，不重复存储标签列表。

### E 域：智能与探索

#### FR-11 群聚效应检测（P2，M4）｜v1.1 新增

**用户故事**：作为用户，我要系统检测链接网络中自然形成的主题群与孤岛，发现知识的结构性机会。

**验收标准**：
1. 基于链接图计算聚类（连通分量/社区检测），输出主题群列表及各群核心笔记（度数最高的节点）；
2. 孤岛笔记（零链接）与悬垂链接（指向缺失目标）清单可查；
3. 群聚结果在图谱视图中高亮呈现（FR-07 联动）；
4. 检测为显式触发或定时任务，不在每次浏览时静默计算。

#### FR-12 探索模式（P2，M4）｜v1.1 新增

**用户故事**：作为用户，我要主动「漫游」卡片盒——随机回顾旧笔记、沿链接深潜、从群聚入口出发——激发意外的连接。

**验收标准**：
1. 随机回顾：按可配置策略（加权：久未访问、低链接数、同群聚）抽取旧笔记；
2. 漫游路径：从当前笔记出发沿链接逐步深潜，记录漫游轨迹；
3. 探索结果可一键转化为结构笔记（FR-08 流流转的衔接）；
4. 探索为显式操作，不自动打扰。

#### FR-13 AI 辅助（P2，M4–M5）｜原 v1.0 FR-06

**用户故事**：作为用户，我要 AI 帮我总结冗长笔记、推荐可能相关的旧笔记，对抗遗忘、发现跨领域连接。

**验收标准**：
1. 单条笔记一键生成中文摘要；多笔记（如一个群聚、一次漫游轨迹）合并综述；
2. 查看/编辑笔记时推荐语义相关的其他笔记（链接 + 全文 + AI 语义综合）；
3. 辅助流转：闪念笔记批量总结候选（「这批闪念可以归纳为……」）；
4. AI 调用显式触发、可关闭；模型与 API Key 可配置；不产生未经请求的自动改写。

### F 域：平台与集成

#### FR-14 多端访问（P2，M5）｜原 v1.0 FR-07

**验收标准**：
1. Web 版响应式适配手机宽度；
2. Tauri 2 打包 Linux/Windows 桌面与 Android，连接同一后端；
3. 各端功能一致（同一套前端代码）。

#### FR-15 vim 插件（P2，M5）｜v1.1 新增

**用户故事**：作为用户，我要留在 vim 里完成常用操作（跳转、补链、检索、看反链），让笔记工具融入编辑器而不是替代它。

**验收标准**：
1. M1 起后端 API 即为「本地服务」形态（REST over localhost），这是插件的前置条件；
2. vim 插件（Vimscript/Lua，随项目仓库交付）提供：`[[编号]]` 补全、光标处链接跳转（`<CR>`/自定义键）、反链与检索结果用 quickfix 展示；
3. 插件只依赖本地 API，不解析笔记库内部实现；
4. 插件功能范围冻结于 M5 详细设计（防止范围蔓延，见 L-08）。

#### FR-16 文件监控（P1，M3）｜v1.1 新增

**用户故事**：作为用户，我在 vim/其他编辑器里改了文件，应用要立刻知道——卡片盒对外部工具永远是敞开的。

**验收标准**：
1. 后端监听笔记目录文件系统事件（新增/修改/删除/移动）；
2. 事件触发派生索引增量更新（FR-18），前端打开的页面自动刷新（WebSocket 推送）；
3. 编辑器保存的原子写（临时文件+rename）模式不产生错误状态（防抖去抖动）；
4. 监控失效（如目录重建）可自动恢复。

#### FR-17 同步与兼容（P2，M5）｜v1.1 新增

**用户故事**：作为用户，我要用 git 管理笔记版本，并随时能用 Obsidian 等主流工具打开我的笔记库。

**验收标准**：
1. git 一等公民：笔记库可整体 `git init`，提供推荐 `.gitignore` 与提交工作流文档；
2. Obsidian 兼容：frontmatter 字段命名、`#tag`、`[[链接]]` 尽量与 Obsidian 惯例对齐；Obsidian 打开本项目笔记库可正常阅读（只读兼容即可，双向兼容不强求）；
3. 文件命名不使用 Obsidian 保留字符；
4. 明确登记本项目语法与 Obsidian 的差异点清单（如 `[[编号]]` vs Obsidian `[[标题]]`）。

### G 域：架构性需求（贯穿）

#### FR-18 存算分离（P0 原则 / P1 落地，M3）｜v1.1 新增

**用户故事**：作为用户，我要文件只负责「存」，计算出来的数据（索引）放在数据库里，并且新文件进来就自动算好——查询要快，但真身永远是文件。

**验收标准**：
1. **文件 = 唯一真身**：笔记内容、链接、标签、顺序关系全部保存在 Markdown 文件中；数据库只是派生缓存（链接索引、反链、标签倒排、图谱边表、全文索引），**可随时删除并全量重建**；
2. **增量计算**：新增/变更 markdown 文件时完成相关派生计算（FR-11 需求原文），不全量重算；
3. M1 无数据库版本先行（O(N) 扫描，接口缝隙注释标记），M3 引入 SQLite 落地本需求，M6 评估 C++ 索引模块替换热点路径；
4. 派生数据库 schema 在详细设计文档定义，并附「删库重建」验证用例（DoD 一部分）。

## 4. 非功能需求

### NFR-01 数据可靠性（最高优先级）

1. **无锁定**：笔记仅存为纯 Markdown 文件（UTF-8，LF），无隐藏数据库；`notes/` 可直接被 git 管理；
2. **写入原子性**：保存先写临时文件再原子替换，崩溃不得损坏既有笔记；
3. **文件自包含**：链接、标签、顺序关系全部存于文件本身；删除派生数据库后，全部关系可从文件重建（FR-18）；
4. **编号稳定性**：编号在层级不变时终生不变；层级调整引发编号变更时，按 FR-03 评审点 R-2 选定策略处理引用一致性；
5. **路径安全**：编号/路径参数在拼接前必须通过合法性校验，杜绝路径穿越。

### NFR-02 性能（单用户本地部署）

| 指标 | 目标值 | 实现阶段 |
|---|---|---|
| 笔记规模 | 5,000 条 | M1 |
| 笔记列表响应 | < 300ms | M1 |
| 笔记详情（M1 O(N) 扫描） | < 500ms @ 5,000 条 | M1 |
| 全局检索 | < 500ms | M3（FR-18 落地后） |
| 文件事件→前端刷新 | < 1s | M3 |
| 标签逻辑查询 | < 500ms | M3 |

M3 起 O(N) 扫描路径全部替换为索引查询；M6 评估 C++ 模块优化热点。

### NFR-03 安全

1. 渲染用户 Markdown 前必须消毒（防 XSS）；
2. API 全输入校验（Pydantic），错误输入返回 4xx 与明确信息；
3. M1–M5 为单用户本地/内网部署，不含认证；对外部署鉴权在 M6 前评估（登记 L-03）。

### NFR-04 可维护性

1. 流程：需求 → 详细设计 → 编码，每阶段评审后进入下一阶段；
2. 后端核心逻辑单元测试（编号策略、wikilink 解析、存储原子性）；API 集成测试；
3. 类型安全：Pydantic v2 / TypeScript strict，前后端模型一一对应；
4. **策略模块化**：编号规则、检索器、AI provider 均为可插拔接口（FR-03 是首例，模式推广）；
5. 代码规范：ruff + 前端默认 lint。

### NFR-05 兼容性

1. 服务端：Python ≥ 3.11（部署环境 3.14）、Linux；
2. 浏览器：Chrome/Edge/Firefox 最新两个大版本；
3. M5 起：Linux/Windows 10+、Android 12+（Tauri 2）；vim 8.2+/Neovim；
4. 笔记文件与 Obsidian（只读）、VS Code、任何标准 Markdown 工具保持文件级兼容（FR-17）。

## 5. 约束与假设

**约束**：
- C1 开发机 Gentoo Linux，Python 无系统 pip，虚拟环境经 ensurepip 自建（已验证）；
- C2 M1 不引入 uv/Docker，用标准 venv + pip + npm；
- C3 阶段闸门制推进，每阶段须用户确认；
- C4 **双射26进制交替编号**与中图编号语法为核心数据格式，一旦笔记库成规模即不可轻易更换，故须在详细设计阶段冻结规格并充分评审。

**假设**：
- A1 单用户使用，无并发写入冲突（M6 前不处理）；
- A2 笔记以中文为主，M3 检索先以子串/FTS 起步，CJK 分词优化后置。
